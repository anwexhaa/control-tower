Build specification

Control Tower

A live freight command centre for Indian enterprise logistics — built as a portfolio piece for FreightFox. This document is the build plan: eight phases, what ships in each, and how we know a phase is done.

Phases8

Why this, and not a landing page

Three findings from FreightFox's public footprint shaped the choice of what to build.

Their site is Webflow

freightfox.ai runs on Webflow with HubSpot forms. No engineer wrote that frontend, so rebuilding it demonstrates nothing to the person reviewing the application.

The product is private

app.freightfox.ai returns 404. Nobody outside the company has seen the TMS. Anything built here is an interpretation, not a copy — and it forces the reader to picture the candidate on the team.

Track is the hard surface

Of six modules, the control tower carries the heaviest frontend load: live positions, dense tables, exception triage, sub-second interaction on thousands of rows. It is the strongest answer to “can you handle complexity”.

What the product is

A single-screen operations console for a national logistics manager at a manufacturer moving full-truckload freight across India. It answers one question continuously: which of my shipments need attention right now, and why.

Everything runs client-side against a deterministic simulation. There is no backend — a seeded generator produces a fleet, and a tick engine advances it through real geography in accelerated time, raising exceptions from the same rules a real control tower uses.

Phase manifest

Phases run in order; each depends on the one before it. Phases 0–4 produce a demoable product on their own — 5–7 are what make it look finished.

Foundation & design system

Stand up the shell and the visual language before any feature work, so every later phase composes instead of restyling.

Build

  • App shell — persistent left rail carrying the six FreightFox modules (Procure · Execute · Track · Settle · Pulse · Decarbonize) with Track live and the rest visibly stubbed; top bar with org switcher, sim clock, and speed control.
  • Primitives — Button, IconButton, Chip, SeverityDot, Badge, Card, Drawer, Modal, Select, Combobox, DateRange, Tooltip, Toast, Skeleton, EmptyState, KeyHint.
  • Routing — file-light hash-free routing via React Router: /track, /track/:tripId, /pulse.

01

Domain model & seed data

1 day

Model Indian FTL freight accurately enough that someone from the industry reads the screen and recognises their own job. This phase is where the project earns its credibility.

Build
  • Types — Trip, Lane, Node (plant / CFS / warehouse / dealer), Transporter, Vehicle, Driver, Consignment, Milestone, Ping, Exception, Document.
  • Geography — 60 real freight nodes with coordinates: Bhiwandi, Gurugram, Hosur, Dahej, Jamshedpur, Sanand, Pantnagar, Guwahati, Vizag, Ludhiana, Nagpur, Kolkata and more.
  • Lanes — 45 corridors with real road distances and transit norms, e.g. Bhiwandi → Bengaluru 985 km / 42 h, Ludhiana → Mumbai 1,630 km / 68 h, Dahej → Bhiwandi 385 km / 18 h.
  • Fleet — Indian FTL vehicle classes with correct payloads: 32 ft SXL (9 MT), 32 ft MXL (15 MT), 22 ft container (10 MT), 20/24/28/32 MT trailers, reefer, tanker, tipper.
  • Documents — LR number, e-way bill with Rule 138 validity (one day per 200 km), GST invoice, weighbridge slip, POD.
  • Seeded PRNG — mulberry32 so every reload produces the identical fleet. A demo that reshuffles on refresh cannot be talked through in an interview.
Milestone sequence — every trip advances through these

indent raised → transporter accepted → vehicle placed → gate-in → loading complete → gate-out / dispatch → in transit → arrived at destination → unloading → POD uploaded → invoiced

Files

src/domain/ types.ts nodes.ts · lanes.ts fleet.ts · transporters.ts documents.ts src/sim/rng.ts · generate.ts

Done when
  • 1,200 trips generate in under 150 ms
  • Same seed → byte-identical output
  • Status mix is plausible: ~62% in transit, ~22% delivered, ~9% at risk, ~7% not started
  • No placeholder strings anywhere in the dataset
Signal

Domain literacy. Anyone can build a table of fake rows; e-way bill validity and 32 ft SXL payloads say you researched the customer.

02

Simulation & rules engine

1.5 days

Make the fleet move, and make problems emerge from movement rather than being hardcoded. This is what turns a mockup into something that behaves.

Build
  • Clock — a simulation clock decoupled from wall time, with pause · 1× · 60× · 600× and a scrubbable 24-hour dial. Ticks at 1 Hz regardless of speed; each tick advances sim-time by the multiplier.
  • Movement — trucks interpolate along a lane polyline using great-circle distance, modulated by a speed profile: highway 45 km/h average, night-halt windows, city-entry slowdown, and a per-trip variance draw.
  • ETA model — remaining distance ÷ trailing average speed, re-projected every tick, with the delta against SLA committed time surfaced as the delay figure.
  • Rules engine — pure functions (trip, now) => Exception[], evaluated per tick, debounced so an exception raises once and then ages rather than re-firing.
  • Event log — append-only stream of every state change, which later feeds the trip timeline and the analytics phase.
  • Web Worker — move the tick loop off the main thread once trip count crosses ~800, so panning the map never stutters the simulation.

03

India map renderer

2 days

Draw the country and the fleet on it, from scratch — no Mapbox, no Leaflet, no tile server. The map is the centrepiece and it should be visibly ours.

Deliberate constraint: hand-rolling the projection and renderer is the single highest-signal decision in this build. Anyone can drop in a map library. Writing a Mercator projection, a quadtree for hit-testing and a canvas draw loop is a different conversation in an interview.

Build
  • Boundary data — real Indian state geometry, simplified with Douglas–Peucker to roughly 40 KB and committed to the repo, so the map has no runtime network dependency.
  • Projection — Web Mercator forward and inverse, with pan and zoom as a single transform matrix; screen ↔ lat/lng conversion used by both rendering and hit-testing.
  • Two-layer render — static geography on an SVG layer, moving fleet on a Canvas layer above it. Canvas because 1,200 markers as DOM nodes will not hold 60 fps.
  • Markers — heading-rotated truck glyphs coloured by severity, with a pulse on freshly raised critical exceptions.
  • Clustering — grid clustering below zoom 5 with a count badge; expands on zoom-in.
  • Hit-testing — quadtree over screen positions for hover and click at cursor speed, rebuilt on transform change rather than per frame.
  • Layers — toggles for lane arcs, plants and warehouses, exceptions-only, and a delay heat overlay by corridor.
  • Interaction — hover card with LR number, vehicle, transporter and ETA delta; click selects the trip and syncs the table and queue.
Files

src/map/ projection.ts quadtree.ts geography.svg.tsx fleetCanvas.tsx clustering.ts layers.tsx src/data/india.simplified.json

Done when
  • 60 fps panning and zooming with 1,200 live markers
  • Hover resolves in under 1 ms via the quadtree
  • Coordinates round-trip through projection and inverse within 0.01°
  • Map is keyboard-pannable and markers reachable via a list alternative
Signal

Canvas, geometry and performance work under a real constraint — the hardest thing in the build, and the part an interviewer will most want to talk about.

04

The control tower screen

2 days

Assemble the operating surface: summary above detail, exceptions triaged, and a thousand-row table that never drops a frame.

Build
  • KPI strip — in transit, on-time delivery %, at risk, delivered today, average delay (h), visibility %. Each tile carries a sparkline of the last 24 sim-hours and a delta against the prior period. Clicking a tile filters everything below it.
  • Exception queue — severity-ordered, grouped by code, with triage actions: acknowledge, assign to a controller, snooze with a reason, resolve with a resolution code. Ageing timers turn amber then red.
  • Trip table — virtualised rows over the full fleet: LR no., lane, transporter, vehicle, status, ETA, delay, exception chips, last ping age. Sortable, multi-column filter, column show/hide, and saved views persisted to localStorage.
  • Filter model — one composable filter object shared by map, queue, table and KPI strip, so the four panes never disagree about what the user is looking at.
  • Command palette — Cmd/Ctrl + K for jump-to-trip by LR or vehicle number, jump-to-transporter, and switching saved views.
  • Layout — resizable split: map on the left, queue on the right, table docked below with a drag handle and a collapse-to-map mode.
Files

src/features/track/ ControlTower.tsx KpiStrip.tsx · Sparkline.tsx ExceptionQueue.tsx TripTable.tsx useVirtualRows.ts filters.ts src/ui/CommandPalette.tsx

Done when

  • Selecting on the map highlights in the table and vice versa
  • Filters compose — lane + severity + transporter simultaneously

Information design under density — deciding what earns space on a screen an operator stares at all day, and keeping four synchronised views honest.

05

Trip detail & documents

1 day

The drill-down. When a controller clicks a flagged trip, everything needed to make the next call is on one surface.

Build
  • Milestone timeline — the eleven-step sequence with actual against planned timestamps, dwell time called out at each node, and future steps shown as projections.
  • Ping trail — inset map of the route travelled with toll-plaza pings plotted, gaps in coverage rendered as dashed segments rather than silently interpolated.
  • Documents — LR, e-way bill with a live validity countdown, GST invoice, weighbridge slip, POD, each with status and a viewer.
  • Telemetry charts — speed and, for reefers, temperature against the permitted band, drawn as custom SVG with the excursion window shaded.
  • Exception history — every exception this trip has raised, with who acknowledged it and when.
  • Actions — notify transporter, revise ETA, raise a manual exception, add a controller note. Each writes to the event log and shows an optimistic update with rollback on simulated failure.
Files

src/features/trip/ TripDetail.tsx Timeline.tsx PingTrail.tsx DocumentPanel.tsx EwayCountdown.tsx TelemetryChart.tsx actions.ts

06

Pulse — performance analytics

1 day

Turn the accumulated event log into the review a logistics head actually runs: who is failing, on which lanes, and what it costs.

Build
  • Transporter scorecard — on-time delivery %, acceptance rate, average delay, detention hours and exception rate per transporter, sortable and rankable.
  • Lane heat table — corridors as rows, weeks as columns, cells shaded by on-time performance, with volume as a secondary encoding.
  • Delay Pareto — root-cause breakdown by exception code with a cumulative line, answering “which two problems cause most of our misses”.
  • Cost view — freight cost per MT and per BTKM by lane, the unit FreightFox itself reports against, with a detention-cost estimate layered on.
  • Charts — all hand-drawn SVG on a shared scale module: one axis system, tabular figures, theme-aware label colours, no charting dependency.
  • Period compare — this week against last, with deltas rendered as signed values in the semantic colours.
Files

src/features/pulse/ Pulse.tsx Scorecard.tsx LaneHeatTable.tsx DelayPareto.tsx CostPerBtkm.tsx src/charts/ scale.ts · axis.tsx bars.tsx · line.tsx

Done when

  • Charts read correctly in both themes

07

Accessibility, performance & ship

1.5 days

Close the gap between “demo that works” and “work someone would merge”.

Build
  • Keyboard — full traversal of the table with arrow keys and type-ahead, roving tabindex in the exception queue, escape-to-close everywhere, and a discoverable shortcut sheet.
  • Screen readers — the map gets an equivalent list view; the exception queue announces new criticals through a polite live region; the table uses proper grid semantics rather than divs.
  • Motion — prefers-reduced-motion stops marker animation and pulses without stopping the simulation.
  • Performance budget — sub-2 s cold load, under 220 KB gzipped JS, no long task over 50 ms during a 60× run. Measured and written down, not assumed.
  • Resilience — error boundary per pane so a chart failure never blanks the console; loading skeletons; genuine empty states with a way out.
  • Responsive — down to tablet at 1024, where the table becomes the primary surface and the map collapses to a summary.
  • Ship — deploy to Vercel, README with architecture notes and the reasoning behind the map decision, plus a two-minute walkthrough recording.
Files

Deliberately out of scope

Naming what we are not building is what keeps eleven days from becoming eleven weeks.

Not building
  • Any backend, database or auth — the simulation is the source of truth
  • The other five FreightFox modules beyond visible stubs in the rail
  • Mobile phone layouts; tablet at 1024 is the floor
  • Real carrier integrations, GPS vendors or FASTag feeds
  • Multi-tenant or role-based permissions
If there is time after phase 7
  • A live spot-auction screen from the Procure module — countdown, bid grid, rank reveal
  • A rebuild of their public payload simulator, as a second smaller piece
  • Natural-language filtering of the trip table, echoing their Nubra AI positioning
